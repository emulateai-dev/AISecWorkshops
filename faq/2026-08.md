## 1. What is an agent, and how is it different from an agent harness?

*Asked: August 2026 session — during the OpenCode setup lab.*

### Short answer

An **agent** is the *decision loop*: a model that is given a goal and a set of tools, and
that chooses — on its own, one step at a time — which tool to call next until the goal is
met or it gives up.

An **agent harness** is the *program that runs that loop*: it holds the conversation,
implements the tools the model can only name, decides what the model is allowed to do,
assembles the context sent on each turn, and renders the result to you. OpenCode is a
harness. Claude Code, Cursor, Aider, and the OpenAI Agents SDK are harnesses.

The model does not read your files. The harness reads your files and tells the model what
it found. That sentence is the whole distinction, and it is also why the two have
completely different attack surfaces.

### What makes something an agent

The useful definition is behavioural, not architectural:

> A system is an **agent** to the degree that the *model*, not the programmer, determines
> the control flow.

Everything with an LLM in it sits somewhere on that spectrum:

| | Control flow decided by | Example |
|---|---|---|
| **Prompt / completion** | Nobody — one shot in, one shot out | "Summarise this paragraph" |
| **Chain / pipeline** | The programmer, fixed at build time | retrieve → rerank → summarise |
| **Router / workflow** | The programmer, with model-chosen branches | classify intent → dispatch to one of 4 handlers |
| **Agent** | The model, at run time, per step | "Fix the failing test" → reads, greps, edits, runs, re-reads |

The practical test: **can you draw the sequence of tool calls before the run starts?** If
yes, it is a workflow. If the sequence depends on what the model sees mid-run, it is an
agent.

### Anatomy of the agent loop

Strip a coding agent down and this is all that is left:

```
        ┌─────────────────────────────────────────────┐
        │                                             │
        ▼                                             │
   ┌─────────┐   messages + tool schemas   ┌───────┐  │
   │ CONTEXT │ ──────────────────────────► │ MODEL │  │
   └─────────┘                             └───┬───┘  │
        ▲                                      │      │
        │                       "call bash('pytest')" │
        │                                      ▼      │
        │                              ┌──────────────┴──┐
        │      tool result appended    │  EXECUTE TOOL   │
        └──────────────────────────────┤ (real side      │
                                       │  effects here)  │
                                       └─────────────────┘
                       loop until: final answer │ budget hit │ user stops
```

Five parts, and only one of them is the model:

| Part | What it is |
|---|---|
| **Goal / instructions** | System prompt + the user's task |
| **Tools** | Named capabilities with typed arguments — `read`, `write`, `bash`, `webfetch`, MCP tools |
| **Context** | The running message history: instructions, task, every tool call and every tool result |
| **The loop** | Call model → parse tool call → execute → append result → call model again |
| **Termination** | Model emits a final answer, or a step/token/cost budget trips, or the user interrupts |

Everything on that list except "call the model" is the harness's job.

### So what is the harness?

The harness is the runtime. It is the part you install, configure, and give credentials
to. For OpenCode specifically:

| Harness responsibility | What OpenCode does | Where you see it in the lab |
|---|---|---|
| **Provider abstraction & auth** | 75+ providers behind one interface; keys in `auth.json` or env vars | [setup/opencode §2–§4](../labs/setup/opencode/README.md) |
| **Model selection** | `/models`, per-agent model config | [§6](../labs/setup/opencode/README.md#6-using-groq-deepinfra-and-ollama-together) |
| **Tool implementations** | `read`, `write`, `edit`, `bash`, `glob`, `grep`, `webfetch` — real code doing real I/O | any session |
| **The loop itself** | Sends the request, parses tool calls, feeds results back | invisible until you trace it |
| **Context assembly** | Builds the system prompt, injects `AGENTS.md`, truncates/compacts history | visible in the trace |
| **Permission gating** | Which tools run silently, which need a confirmation | `permission` in config |
| **Extension points** | Plugins, MCP servers, custom agents, hooks | [§8](../labs/setup/opencode/README.md#8-optional--dump-the-raw-llm-requests-and-responses) |
| **Session state & UI** | The TUI, session persistence, `opencode stats` | every run |

Swap Groq for Ollama and the agent's *behaviour* changes; the harness is identical. Swap
OpenCode for Claude Code with the same model and the harness changes; the model is
identical. They are independently replaceable, which is exactly why they should be
threat-modelled separately.

### Side by side

| | Agent | Harness |
|---|---|---|
| **What it is** | A pattern: model + tools + loop, model-directed | A program: the runtime that executes that pattern |
| **Where it lives** | Emerges at run time, in the message history | On disk, as software you install |
| **Substance** | Weights + a prompt + tool schemas | Code, config files, credentials, a UI |
| **Decides** | *Which* action to take next | *Whether* that action is permitted, and *how* it executes |
| **Examples** | A coding agent, a research agent, a support agent | OpenCode, Claude Code, Cursor, Aider, LangGraph, OpenAI Agents SDK |
| **Fails by** | Being persuaded — injection, jailbreak, goal hijack | Being misconfigured or over-permissioned |
| **Fix looks like** | Better prompts, better model, guardrails, evals | Sandboxing, allowlists, least privilege, secret hygiene |

A useful mental shorthand: **the agent is the driver, the harness is the car.** The driver
decides where to go. The car decides how fast it *can* go, whether the doors lock, and
whether there are brakes at all. Prompt injection convinces the driver. A bad harness
means the brakes were never installed.

### See the split for yourself

The fastest way to make this concrete is to read one real request on the wire. Enable the
trace plugin from
[setup/opencode §8](../labs/setup/opencode/README.md#8-optional--dump-the-raw-llm-requests-and-responses),
run any task, then dump it:

```bash
./labs/setup/opencode/trace-to-jsonl.sh ~/opencode-trace/<file>.html | jq .
```

In that JSON, sort what you see into two piles:

- **Harness-authored** — the system prompt, the tool definitions and their JSON schemas,
  the file contents pasted in as tool results, the truncation markers. You never typed any
  of it. The harness decided all of it.
- **Model-authored** — the assistant messages and the tool calls with their arguments.

The model only ever emitted the second pile. Everything in the first pile is harness
policy, and every byte of it is attacker-reachable if any of it came from a file, a web
page, or an MCP server.

### Why this matters for red teaming

The two layers fail differently, so they are tested differently:

| Layer | Representative attack | Labs |
|---|---|---|
| **Model / agent** | Direct + indirect prompt injection, system prompt extraction, goal hijacking, multi-turn social engineering | [Folly](../labs/agents/red-teaming/folly/README.md), [EDR](../labs/agents/red-teaming/edr/readme.md), [CS Agent](../labs/agents/red-teaming/open-ai-cs-agent/readme.md) |
| **Harness** | Over-broad tool permissions, config/plugin poisoning, credentials readable by the agent's own `read` tool, traces holding whole conversations, unsandboxed `bash` | [setup/opencode](../labs/setup/opencode/README.md), [DVMS / MCP](../labs/mcp/red-teaming/dv_mcp_labs/readme.md) |

The bridge between them is the tool boundary, and that is where most real incidents land:
a *model-layer* compromise (injected instruction) cashed out through a *harness-layer*
privilege (an unrestricted `bash`, or an MCP server with write access). Neither layer is
individually at fault, which is why testing only one of them misses the finding.

Two consequences worth stating plainly:

1. **A safer model does not make an unsafe harness safe.** Alignment reduces how often
   the model *wants* to do the harmful thing. It does nothing about what the harness will
   *let* it do when it is persuaded.
2. **MCP servers are harness surface, not model surface.** Adding an MCP server adds tools
   and tool descriptions — text the harness injects into context and code the harness will
   execute. Tool poisoning and rug-pull attacks work at that layer, which is why they get
   their own lab track.

## 2. How do you design a secure agent?

*Asked: August 2026 session.*

**Status: Open** — answer pending.

Scope agreed in the session, to be covered when this is written up:

- Trust boundaries in an agent: which of {system prompt, user input, retrieved data, tool
  output, MCP tool descriptions} is trusted, and why the honest answer is "only the first"
- Least-privilege tool design — narrow typed tools over a general `bash`
- Permission gating, human-in-the-loop, and where confirmation actually helps
- Sandboxing and blast radius: filesystem, network egress, credentials
- Handling untrusted content: provenance, quarantine, and why "instructions in data" cannot
  be prompt-engineered away
- Output sinks and exfiltration paths (URLs, markdown images, tool arguments)
- Budgets, loop limits, and kill switches
- Logging, tracing, and post-incident reconstruction
- Evals and continuous red teaming as a release gate

Builds directly on [Q1](#1-what-is-an-agent-and-how-is-it-different-from-an-agent-harness):
most of the controls above live in the **harness**, not the model.
